# Native Linux/x86-64 runtime parity goal

## Status and scope

This is the active plan for bringing `crabc`, `crabc-libc`, `crabc-ldso`, the
CRT/sysroot, and `crabc-rs` to the same selected capability boundary as the
current Linux/AArch64 runtime.

It authorizes native Linux/x86-64 little-endian work only, with Linux 5.10 as
the kernel baseline. It does not authorize AArch64 emulation, another
architecture, a portability framework, or public x86-64 support. Until every
promotion gate below passes, Linux/AArch64 little-endian remains the only
supported public platform.

This document is deliberately a forward-looking goal and handoff. The exact
completed evidence belongs in
[`compat/x86_64/parity.toml`](compat/x86_64/parity.toml) and
[`compat/x86_64/README.md`](compat/x86_64/README.md), not in a growing list of
historical one-command checkpoints.

## What parity means

Parity is semantic coverage of the selected AArch64 runtime profile, not a
symbol count or a mechanical C-wrapper count. Each selected capability needs
an x86-64-native implementation, any required target ABI/layout proof, and
repeatable native evidence.

The completed target includes all of the following:

- `crabc-core`: x86 syscall, ELF/vDSO, TLS/thread-pointer, atomics/futexes,
  signal-frame, floating-point, and typed kernel-record foundations.
- `crabc-rs`: the same useful native runtime capability accounting as AArch64,
  exposed as an idiomatic Rust layer rather than a C ABI mirror.
- `crabc-libc`: the selected C/POSIX runtime, headers/layouts, errno/TLS,
  pthread/TLS, filesystem/process/signal/time/socket/resolver behavior, and
  text/locale/math/stdio profile.
- `crabc-ldso`, CRT, builtins, and an owned sysroot: native static and dynamic
  startup, dynamic loading, TLS, linking, and source-build behavior.
- Native qualification: ABI and behavioral differentials, OS/libc/pthread/
  resolver/loader gates, Rust-std/LTO consumers, source builds, capability
  accounting, and required performance evidence.

The retained profile remains the one in [`SCOPE.md`](SCOPE.md) and
[`COMPATIBILITY-PROFILE.md`](COMPATIBILITY-PROFILE.md): musl 1.2.6 is the C
and POSIX oracle; Rustix is test-only; glibc is never an oracle or fallback;
the resolver is bounded to conventional system files and A/AAAA/CNAME over
UDP/TCP; and there is no NSS, DoH/DoT, mDNS, IDNA policy, general locale
database, or hand-written cryptography.

Fixed mimalloc port work and evidence expansion are paused. Its retained
native x86 evidence is private allocator provenance, not progress toward this
runtime target.

## Current starting point

The parity ledger records a verified native foundation: pinned-musl oracle
provenance, x86 architecture primitives, a broad but bounded direct
`crabc-rs` subset, selected source-only C runtime leaves, checked relative
loader/image work, and a static-PIE CRT foundation. The direct facade now also
includes a complete socket/address transport family: socket lifecycle,
IPv4/IPv6 UDP, IPv4 TCP, typed options, `SIOCATMARK`, and vectored/batched
messages.

These are foundations, not partial public-platform claims. In particular,
source-only libc leaves do not select `crabc-libc`; direct Rust evidence does
not select record-owning facade families; and relative relocation/static PIE
does not provide a dynamic loader or owned sysroot.

## Remaining implementation milestones

Work in these subsystem-sized blocks. A block may contain several focused
tests and oracle fixtures, but it is not complete until its whole stated
family is implemented, evidenced, recorded in the ledger, and integrated into
the canonical native lane.

| Order | Milestone | Required outcome |
| --- | --- | --- |
| 1 | Network completion | Finish `crabc-rs` networking as one family: interface/device snapshots and names, bounded resolver transport and policy, and `/etc/hosts`, `/etc/services`, `/etc/protocols`, and `/etc/resolv.conf` handling. Use deterministic local UDP/TCP DNS fixtures, no external DNS. Keep C resolver ABI work for the C-runtime milestone. |
| 2 | Remaining Rust runtime families | Complete the remaining `facade.record-owning` surface in coherent domain blocks: filesystem path-core (directory streams, temporary files, xattrs, CWD mutation, and selected path metadata), process/child lifecycle and execution, thread/process controls, signal/event extensions, and the remaining time/VM/system records. The exact selected capability list remains closed in `compat/x86_64/parity.toml`. |
| 3 | C runtime bootstrap and ABI | Turn the x86 C leaves into a selected `crabc-libc` artifact: headers/layouts, syscall-to-errno/TLS boundary, POSIX descriptor/filesystem/process/signal/time behavior, pthread/TLS, text/locale/math/stdio, bounded C resolver, then C ABI compatibility closure. Preserve musl differentials and do not claim a C feature from an isolated source object. |
| 4 | Dynamic runtime and owned toolchain | Complete the x86 dynamic loader, dynamic CRT entries, compiler-helper linkage, static TLS, and reproducible owned sysroot. Prove static and dynamic application startup through the installed artifacts, never ambient target CRT, compiler runtime, loader, or headers. |
| 5 | Native qualification and promotion | Run the x86 ABI/differential, OS/libc/pthread/signal, resolver-network, loader/corpus, Rust-std/LTO, source-build, capability-accounting, and required performance gates. Only then change the public support boundary. |

### First remaining block: network completion

The next implementation block is deliberately broad, building on the proved
socket transport boundary:

1. Prove x86 interface ABI records and bounded read-only interface operations
   in `crabc-rs/src/netdevice.rs`; use stable loopback/self-consistency
   assertions rather than host-specific interface ordering or counts.
2. Enable and prove the existing bounded resolver transport in
   `crabc-core/src/resolver.rs` and `crabc-rs/src/resolver.rs` with local-only
   UDP and TCP fixtures. Cover wrong-ID filtering, malformed packets, timeout
   and failover, TCP fallback after truncation, bounded buffers, and partial
   I/O.
3. Enable and prove `crabc-rs/src/netdb.rs` and related bounded parsers using
   deterministic caller-supplied fixtures plus narrow system-file smoke tests.

The block is complete only when its direct Rust APIs, ABI records, oracle
fixtures, native tests, canonical runner integration, and parity-ledger
entries land together. It must not expose generic socket/ioctl APIs, a public
C socket/resolver ABI, NSS/provider plugins, or external-network test
dependencies.

## Parallel work lanes

To keep throughput high without erasing dependency boundaries, work may fan
out along these lanes:

- **Facade lane:** network completion first, then the remaining filesystem,
  process/child, thread, signal/event, and time/VM blocks.
- **C-runtime lane:** header/layout closure and errno/TLS integration, then
  selected C/POSIX and pthread/TLS behavior. It may proceed alongside facade
  work but must converge before the ABI-compatibility gate.
- **Runtime-artifact lane:** loader image/relocation and static-PIE foundations
  are already available; dynamic loader/CRT/sysroot work begins once its C
  header, TLS, and ABI prerequisites are real artifacts rather than leaves.
- **Qualification lane:** extend deterministic x86 harnesses as each block
  lands. Full C/POSIX, corpus, Rust-std, source-build, accounting, and
  performance promotion waits for the artifact chain.

Do not turn a missing dependency into another tiny goal. When a subsystem has
several independent records or syscalls, plan and implement its full useful
contract together; split only where an actual safety, ABI, or artifact
dependency makes that necessary.

## Evidence and promotion rules

For every block:

1. Read the governing scope/profile/status documents and the relevant AArch64
   implementation, tests, and ledger entries.
2. Specify the exact native contract and write focused observable regressions.
3. Implement the target-specific code without emulation or ambient fallback.
4. Add native raw-kernel and/or pinned-musl evidence for every ABI boundary,
   then run the focused native command and the relevant aggregate lane.
5. Update `compat/x86_64/parity.toml`, structural checks, and the nearest
   documentation with the exact admitted boundary and exclusions.

`compat/x86_64/parity.toml` remains the closed promotion ratchet. Its required
families cover architecture, facade, libc, loader, CRT/sysroot, compatibility,
consumer, accounting, and performance gates. Passing a foundation command or
one facade family never promotes x86-64 by itself.

## Handoff

The current checkpoint completes and validates the native x86 socket/address
transport family. Resume with the network-completion block above, not another
isolated socket option or filesystem syscall.

Before resuming implementation:

1. Read `SCOPE.md`, `COMPATIBILITY-PROFILE.md`, `STATUS.md`, this file, and
   `compat/x86_64/parity.toml`.
2. Confirm the checkpoint with:

   ```bash
   ./scripts/dev-x86_64.sh socket-transport-reference
   ./scripts/dev-x86_64.sh facade
   python3 scripts/check_structure.py
   python3 compat/x86_64/validate_parity_ledger.py --check
   ```

3. Fetch `origin` and rebase only if `origin/main` is not already an ancestor
   of the committed local branch; never use AArch64 emulation.
4. Keep mimalloc paused unless the user explicitly reprioritizes it.

Do not run formatters, linters, pre-commit hooks, or push a remote unless the
user explicitly asks.
