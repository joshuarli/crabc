# Native Linux/x86-64 runtime parity goal

## Status and boundary

This is the active staged program for native Linux/x86-64 little-endian
support. It is not a claim that `crabc`, `crabc-libc`, `crabc-ldso`, or
`crabc-rs` supports x86-64 today. Until its promotion gates pass, the public
support boundary remains Linux/AArch64 little-endian as stated in `SCOPE.md`,
`COMPATIBILITY-PROFILE.md`, and `STATUS.md`.

The target is Linux 5.10 or newer, native x86-64 execution only. Do not use
AArch64 emulation as evidence, add a generic portability framework, or broaden
this goal to another architecture, endianness, kernel, or operating system.

## Completion accounting

[`compat/x86_64/parity.toml`](compat/x86_64/parity.toml) is the closed,
machine-readable x86 parity ledger. It maps the selected AArch64 capability
and gate surface into ordered x86 families, their ABI/header prerequisites,
native evidence, oracle, and promotion state. Its validator rejects missing,
duplicate, or stale accounting; passing a narrow foundation command never
changes the public support boundary. This document is the readable goal and
dependency map; the ledger is the completion ratchet.

### Current verified foundation

The closed `./scripts/dev-x86_64.sh musl-oracle` command source-builds and
verifies pinned musl 1.2.6 beneath `/opt/musl-1.2.6`, including its compiler
specification, x86 interpreter, and mapped runtime `libc.so`. It is oracle
toolchain provenance only: it is neither a crabc artifact nor a compatibility
differential result.

The closed `./scripts/dev-x86_64.sh header-abi-reference` command records the
pinned x86 SysV LP64/x87 C baseline: 16-byte storage/alignment for 80-bit
extended `long double`, the corresponding complex calling convention, and
the 32-byte musl `fenv_t`. It deliberately compiles no crabc public header;
the reference baseline itself is not public x86 C-header support.

The separate `./scripts/dev-x86_64.sh header-abi-project` command places the
project include directory first and compile-checks the source-only x86
`fenv`, `float`, and fundamental-type declarations against that baseline in
both SSE and x87 evaluation modes. It has no link step and does not select
`crabc-libc`: all remaining installed headers and C runtime behavior remain
unadmitted until their own target-specific contracts have evidence.

The separate `./scripts/dev-x86_64.sh sys-reg-header-abi` command records the
27 x86 ptrace register-index macros in the project `<sys/reg.h>` against the
pinned musl declaration oracle. It is a compile-only declaration slice; it
does not provide ptrace behavior or select `crabc-libc`.

The separate `./scripts/dev-x86_64.sh types-header-abi` command checks the
staged `<bits/alltypes.h>` and `<sys/types.h>` C and C++ declarations against
pinned musl: `nlink_t`, signed `blksize_t`, C's opaque-pointer `pthread_t`,
C++'s integer `pthread_t`, and the named opaque pthread object layouts. It is
compile-only and does not establish pthread behavior or select `crabc-libc`.

The separate `./scripts/dev-x86_64.sh syscall-header-abi` command compares all
384 `__NR_*` and 384 `SYS_*` project `<sys/syscall.h>` macros with pinned musl
1.2.6. It is a declaration-only source slice; a complete numeric namespace
does not provide syscall wrappers or a C runtime artifact.

The separate `./scripts/dev-x86_64.sh mm-abi-reference` command pins the musl
x86 `mmap`/`mprotect`/`munmap` numbers and the closed mapping flag constants
used by the native Rust mapping slice. It neither compiles project headers nor
selects a C ABI artifact.

The first native Linux/x86-64 core boundary is implemented and checked through
the deliberately closed `./scripts/dev-x86_64.sh core` runner. Its evidence is
the `crabc-core` `x86_64-unknown-linux-musl` lib suite, which directly covers
the x86 syscall argument registers through `openat` mode and six-word futex
behavior, `%fs` thread-pointer identity, x86 ELF/vDSO discovery including
`__vdso_gettimeofday`, x87 plus MXCSR floating-point-environment updates, and
a raw `rt_sigaction`/`SA_RESTORER` install, exact-thread delivery, and
`rt_sigreturn` round trip.

The separate `./crt/run-x86_64.sh static-pie` runner verifies the deliberately
bounded static-PIE CRT foundation: `rcrt1.o`, `crti.o`, and `crtn.o` apply
checked `R_X86_64_RELATIVE` RELA/RELR records, seal GNU RELRO, enter the
static lifecycle, and reject a mutated non-relative relocation. It does not
provide dynamic `crt1.o`/`Scrt1.o`, sysroot installation, or a loader handoff.

The separately fixed `./scripts/dev-x86_64.sh ldso-relocation` command runs
the source-only `ldso/src/x86_64_relocation.rs` test module under native
Linux/x86-64. It proves checked symbol-free `R_X86_64_RELATIVE` RELA and ELF64
RELR processing, including complete preflight, table-target separation, and
no-mutation rejection of duplicate targets. It is not selected by
`crabc-ldso`, does not provide an ELF interpreter or symbol lookup, and does
not relax the dynamic-loader completion obligation below.

The closed `./scripts/dev-x86_64.sh libc-syscall` command independently
compiles the unintegrated `libc/src/c_abi/x86_64/syscall.rs` source and
behavior-tests raw `openat`, `setsockopt`, and `mmap` calls through all six
x86 syscall argument registers. It establishes neither a `crabc-libc` binary
nor any C layout, errno, TLS, pthread, or header support.

The closed `./scripts/dev-x86_64.sh libc-errno-tls` command independently
compiles `libc/src/c_abi/x86_64/errno.rs` and links a native C fixture
through the installed project `errno.h`. It proves a local initial-TLS datum
with `R_X86_64_TPOFF*`, no `__tls_get_addr` resolver path, zero initialization,
and isolated main/pthread `errno` slots. This remains one source-only C leaf:
it does not select `crabc-libc` or establish complete C layouts, pthread
behavior, headers, or syscall-to-errno translation, and is not a musl
differential or compatibility-oracle gate.

The closed `./scripts/dev-x86_64.sh libc-setjmp` command independently
compiles the unintegrated `libc/src/c_abi/x86_64/setjmp.rs` leaf and links a C
fixture through the staged project `<setjmp.h>`. It differentially executes
the same fixture against pinned musl, then proves the x86 200-byte
machine/signal-mask record, register and stack restoration, direct aliases,
zero-to-one `longjmp` conversion, and `sigsetjmp` mask restoration. This is
still source-only evidence: `crabc-libc` does not select it and no broad C
runtime or x86 public-support claim follows from the checkpoint.

The direct `crabc-rs` foundation admits record-independent modules
(`buffer`, `collections`, `fd`, `fenv`, `ffi`, `io`, `ioctl`, `memory`,
`numeric`, scalar `param` observations, `pipe`, `rand`, `stdio`, and `text`),
the scalar `eventfd2` counter API, a closed `mm::{mmap, mmap_anonymous,
mprotect, munmap}` slice, and the separately proved x86 signal-action/raise
boundary. The mapping slice permits `PROT_NONE` (the empty set) plus only
`READ`/`WRITE`/`EXEC` protections and exactly one `PRIVATE` or `SHARED` mapping
mode; it rejects `MAP_32BIT`, `MAP_FIXED`, `MAP_FIXED_NOREPLACE`, other fixed
mappings, architecture-specific protection bits, and all wider VM policy.
`param` does not yet expose `AT_EXECFN` as a safe pathname reference: a raw
auxv word alone does not prove pointer provenance. Native evidence covers
x87/MXCSR fenv state, direct
descriptor/pipe I/O including Linux/x86-64's `O_DIRECT` packet-mode bit,
vector and positioned I/O through the 64-bit offset split, `preadv2`/
`pwritev2` current-offset and flag rules, descriptor duplication and `fcntl`
flags, ioctl encoding and typed `EBADF`, stable scalar aux-vector
observations, eventfd `NONBLOCK`/`CLOEXEC` counter reset and semaphore
behavior, anonymous mapping protection transitions, a sparse file mapping at
a full 64-bit 4 GiB offset, and an installed handler's x86 `rt_sigreturn`
round trip. Filesystem/stat, poll/ppoll/pselect, epoll, signalfd, remapping,
locking, mapping synchronization/advice/residency, networking, process/thread/
time, loader/runtime, and every other AArch64-record-owning facade family
remain absent until they have their own x86 ABI proof.

Its repeatable native evidence is deliberately fixed at
`./scripts/dev-x86_64.sh facade`; that command is not a general x86 Cargo
entry point and cannot widen the admitted subset.

These are only foundation checkpoints. In particular, they do not supply an
x86 C `fenv_t` ABI, `crabc-libc`, `crabc-ldso`, a complete CRT/sysroot, or a
generally admitted `crabc-rs` target; its bounded direct subset remains a
separate vertical slice and every omitted family remains a promotion
obligation below.

## Definition of parity

Parity means the same useful modern Unix runtime capability boundary that is
currently implemented and evidenced for Linux/AArch64. It is not a symbol
count, a C-wrapper count, or allocator-only parity. Each selected capability
must have an x86-64-native implementation, architecture-appropriate ABI proof,
and its own native evidence.

A completed x86-64 target includes:

- `crabc-core`: typed Linux kernel and vDSO primitives, x86-64 syscall ABI,
  thread-pointer/TLS access, atomics, futexes, signals, and architecture
  invariants.
- `crabc-libc`: the supported C/POSIX ABI, public headers and layouts, errno
  and TLS, pthread/TSD behavior, files/descriptors, process and signal
  behavior, memory mapping, time, stdio, locale/text/encoding, sockets,
  resolver, math, and the other currently supported AArch64 capability
  families.
- `crabc-ldso`: x86 ELF startup and finalization, relocation and symbol-scope
  rules, loader TLS, interpreter state, and the `RuntimeV1` bridge.
- CRT and sysroot artifacts: startup objects, compiler helpers, static and
  dynamic linking, static TLS, and source-build behavior that matches the
  current AArch64 contract.
- `crabc-rs`: idiomatic, typed native runtime operations with the same semantic
  accounting as AArch64. It must not become a mechanical C ABI wrapper layer.

The required observable capability families include descriptor and filesystem
operations, pipes, process creation and execution, credentials and controls,
signals, pthread/TLS, sockets, `mmap`, clocks and timers, stdio, resolver
behavior, dynamic linking, ABI/linkage, and the existing Rust-facade surface.

## Compatibility profile retained on x86-64

The x86-64 target retains the current AArch64 profile rather than widening it:

- locales are `C`, `POSIX`, and `C.UTF-8`; Rust text is UTF-8;
- resolver behavior is bounded to conventional `/etc` files and the documented
  A/AAAA/CNAME UDP/TCP retry/failover profile;
- no NSS/provider plugins, bundled tzdata, gettext framework, IDNA policy,
  async runtime, process supervisor, or security-policy framework;
- no hand-written cryptography; and
- musl 1.2.6 remains the C/POSIX oracle, Rustix remains a pinned native-API
  and test oracle, and glibc is never an oracle or fallback.

Existing native x86-64 `crabc-mimalloc` evidence is preserved as private
allocator evidence only. It does not establish a supported x86 C runtime,
loader, CRT/sysroot, Rust facade, or public x86 platform.

## Architecture-specific proof obligations

Before a capability is promoted, prove its x86-64-specific contract where
applicable: syscall numbers and calling convention; ELF machine, relocations,
code model, assembly, and linkage; TLS/thread-pointer model; atomic and futex
ordering; signal frames; `setjmp`/unwind/compiler helpers; data layout and
little-endian assumptions; CRT startup; and dynamic-loader behavior.

Each vertical slice follows: contract and capability classification, focused
test, implementation, direct ABI/boundary proof, musl/POSIX or other named
oracle evidence, then ledger and status documentation. Keep x86-64 ledgers and
reports separate from AArch64 measurements.

## Required execution order

1. Keep the parity ledger exhaustive and native-only, establish the pinned
   musl 1.2.6 oracle, then close architecture foundations: syscall register
   ABI, ELF/vDSO, thread pointer, floating-point state, signal frame/restorer,
   and target records.
2. Admit `crabc-rs` only family by family. A native compile is insufficient:
   every record passed to Linux must have its x86 layout and direct behavior
   proof before that API is exposed.
3. Port the C boundary in the same order: x86 syscall/assembly primitives,
   headers and layouts, errno/TLS and pthread state, then the selected C/POSIX
   families with musl 1.2.6 differential evidence.
4. Complete x86 CRT/sysroot and `crabc-ldso` as one bootstrapping chain:
   static and dynamic entries, relocations, TLS, loader handoff, and source
   builds. Do not promote a partial entry object as a sysroot.
5. Run the full native gate set and capability ledgers, then performance gates
   where the current AArch64 contract requires them. Only this final step can
   alter the public platform boundary.

## Promotion gates

Native x86-64 support can be declared only when all selected AArch64-equivalent
families pass their corresponding x86 evidence:

1. header, ABI, static-link, loader, TLS, signal, pthread, resolver, OS, and
   C/POSIX/libc-test gates;
2. `crabc-rs`, Rust-std-dependent, LTO, CRT/sysroot, static-TLS, and source
   build gates;
3. capability ledgers with no unaccounted selected surface; and
4. qualified performance evidence wherever the current AArch64 completion
   contract requires it.

Only then update the public scope/profile/status/dashboard documents to name
x86-64 as supported. Before then, describe this work as a future goal or
in-progress native evidence, never as current platform support.
