# Native Linux/x86-64 parity — completion contract

## Mission

Bring `crabc-core`, `crabc-rs`, `crabc-libc`, `crabc-ldso`, the CRT and
compiler-builtins artifacts, and the installed crabc sysroot to full native
Linux/x86-64 little-endian parity with the frozen Linux/AArch64 selected
runtime profile.

This file is an execution contract. It is not a status journal, evidence
archive, or list of historical one-command checkpoints. A task phrased as
**“implement to `x86-64.md` to full completion”** authorizes the agent to carry
this program through every phase below, including integration, qualification,
and the final public-support transition. Do not stop after adding private
artifacts, closing a convenient subset, producing a handoff, or reaching a
locally stable checkpoint.

Continue autonomously until the exact completion predicate in this document is
true. Resolve ordinary implementation questions from the frozen baseline,
`SCOPE.md`, `COMPATIBILITY-PROFILE.md`, the relevant AArch64 implementation,
pinned musl 1.2.6, the System V AMD64 ABI, Linux 5.10, tests, and executable
contracts. Ask the user only when work would require:

- changing the frozen AArch64 baseline;
- widening or contradicting the project scope;
- adding a framework-scale, native-code, or otherwise unusually broad
  production dependency; or
- performing an external operation that the repository contract does not
  authorize, such as pushing a remote.

The size or difficulty of the remaining work is not a reason to stop, narrow
the target, or return a partial-completion claim.

## Scope

The implementation target is:

- Linux/x86-64 little-endian;
- the `x86_64-unknown-linux-musl` Rust target where a Rust target name is
  required;
- Linux 5.10 as the kernel minimum;
- native x86-64 execution only;
- the selected runtime profile defined by `SCOPE.md` and
  `COMPATIBILITY-PROFILE.md`;
- pinned musl 1.2.6 as the C/POSIX source, ABI, and behavior oracle;
- the System V AMD64 ABI and Linux ELF ABI as architecture and object-format
  contracts; and
- Rustix only as a test oracle where already permitted, never as a production
  runtime dependency.

Do not run AArch64 implementation or qualification suites as part of this
campaign. Do not modify AArch64 runtime behavior merely to make x86-64 easier.
The frozen AArch64 material is an immutable comparison target, not an active
implementation lane.

Glibc is never an oracle, compatibility implementation, target input, or
fallback. Ambient musl, compiler-runtime, CRT, loader, target-header, or target
library inputs are likewise forbidden from candidate artifacts unless a test
is explicitly executing the separate pinned-musl oracle arm.

## Exact definition of full completion

The campaign is complete only when all of the following are simultaneously
true in a clean native x86-64 worktree.

### Baseline and accounting

1. The frozen-baseline validator passes without refreshing any AArch64 input.
2. All 223 frozen capabilities are mapped exactly once.
3. No capability remains `missing` or `selected-private`; every capability has
   the promotion-recognized completed state and complete evidence required by
   its owning family.
4. All 26 required families have `status = "foundation-verified"` in
   dependency order.
5. No required family is omitted, duplicated, replaced by an artifact-only
   proxy, or waived.
6. The capability-accounting gate derives its answer from the frozen baseline
   and current x86 ledger rather than hard-coding success.

### Owned static product

7. A reproducible installed x86 sysroot builds and runs both ordinary static
   `ET_EXEC` and static PIE applications.
8. The final static artifacts use only the installed crabc headers, CRT
   objects, `libc.a`, crabc compiler-builtins archive, allocator backend, and
   explicitly admitted application objects as target inputs.
9. Static startup, Initial TLS, errno, pthread/C11 threads, allocation,
   ordinary exit, constructors/destructors where applicable, stdio,
   filesystem, process, signal, time, socket, and bounded resolver behavior all
   execute through the owned runtime.
10. A stable, reproducible link interface exists. It may be a driver
    specification, wrapper, or completely documented direct-link recipe, but
    it must select owned inputs deterministically and reject ambient target
    CRT, libc, libgcc, compiler-rt, loader, and headers.
11. Two clean sysroot builds are byte-for-byte reproducible for the declared
    regular-file artifact set, and an extracted copy passes the same static
    smoke suite.

### Owned dynamic product

12. The installed sysroot builds and runs dynamic PIE and dynamic non-PIE
    applications through the installed crabc interpreter and shared libc.
13. The general loader—not a fixed graph—implements the frozen selected
    dependency search, object mapping, relocation, symbol scope, RuntimeV1,
    loader/libc handoff, and public `dl*` contracts.
14. Initial-exec and dynamic TLS, module IDs, DTV construction and growth,
    `__tls_get_addr`, newly created threads, initially loaded DSOs, and
    runtime-loaded DSOs interoperate under one coherent loader/pthread/TCB
    ownership model.
15. Executable and DSO preinitialization, initialization, finalization,
    ordinary process exit, `dlclose`, retained mappings and reopen behavior,
    loader locking, callbacks, and admitted reentrancy match the frozen
    selected profile.
16. Dynamic consumers use the installed shared libc, interpreter,
    compatibility interpreter alias where required, CRT, builtins, headers,
    and link specification with no ambient target fallback.
17. Two clean installed dynamic artifacts are reproducible, and an extracted
    copy passes the same dynamic smoke suite.

### Qualification and public support

18. Every native x86 family aggregate passes, followed by the complete ordered
    qualification chain:

    ```text
    compat.abi-differential
      -> compat.posix-process
      -> compat.resolver-network
      -> compat.loader-corpus
      -> consumer.rust-std-lto
      -> consumer.source-build
      -> capability.accounting
      -> performance.release
    ```

19. The selected AArch64 consumer set is reproduced on x86; do not substitute
    easier consumers or expand the product scope merely to create a new test.
20. Release-mode native performance evidence satisfies the existing
    performance contract or a narrowly documented x86-specific equivalent
    justified by the same project goals. No performance family is waived.
21. The final promotion validator computes `promotion_ready = true` from the
    completed contracts.
22. Only after items 1–21 pass, set the x86 public boundary to supported,
    update the relevant public compatibility documents, and make
    `public_support = true` a validated consequence rather than an assertion.
23. The final clean-worktree aggregate rerun passes after the public-boundary
    change.

A private fixture, selected export, verified artifact, verified slice, fixed
loader graph, static-only demonstration, dynamic-only demonstration, or
passing focused test is never equivalent to full completion.

- GitHub Actions, CI workflow design, CI runner setup, and changes under
  `.github/workflows/`;
- AArch64 implementation changes or a moving AArch64 parity target;
- another CPU architecture, big-endian support, 32-bit support, non-Linux

- glibc compatibility as an oracle or fallback;
- NSS, PAM, mDNS, DoH, DoT, DNSSEC, IDNA policy, a provider/plugin framework,

  `SCOPE.md`;

- treating standalone allocator parity as runtime or public-support closure; and
- unrelated cleanup, formatting, linting, pre-commit work, or remote pushes.

currently accepted production allocator backend and wrapper architecture

coordinates the two. That program neither changes the frozen runtime baseline
nor waives any runtime gate. AArch64 allocator work remains paused.

## Progress and scheduling rules

Use `plan.md`'s throughput policy: widen dependency-ready component/family
batches when leaf-sized work is slowing delivery, reuse existing matrices,
and run expensive suites at integration checkpoints rather than on every edit.
This changes process frequency, not family or final acceptance predicates.

The primary progress measures, in descending order, are:

1. a product gate becoming complete;
2. a required family moving from `planned` to `foundation-verified`;
3. a capability moving from `missing` or `selected-private` to its completed
   state;
4. a verified slice closing a named family-completion obligation; and
5. removal of an explicitly recorded hard blocker on one of those transitions.

Artifact counts, export counts, test-file counts, commit counts, lines of code,
and paragraphs of evidence are diagnostics only.

For each work package, identify the completion blocker, relevant contract,
nonoverlapping ownership, and useful acceptance checks. A concise assignment
is enough; do not create a separate planning artifact or repeat fields already
defined by the owning family/product contract.

A work package that can say only “adds an export,” “adds evidence,” “ports one
symbol,” or “matches one musl source file” is not schedulable. It must first be
combined into a coherent capability, verified-slice, family, integration, or
qualification block.

Small independent leaves may be implemented together inside such a block.
They must not each acquire an independent planning cycle, bespoke runner,
settlement paragraph, and merge solely because that pattern is convenient.

If successive patches are not closing these obligations, redirect work toward
the actual blocker and widen the batch where useful. Do not wait for a commit
count or create a replanning ceremony. Unfinished gates still require continued
implementation, not a completion claim.

Preserve the exact validated `parity.toml` dependencies unless this contract
explicitly corrects an accidental coupling such as the static/dynamic issue
above. The campaign-level critical path is:

    -> libc.posix-runtime
      -> libc.pthread-tls
        -> libc.text-math-locale-stdio
          -> libc.resolver
            -> libc.c-abi-compat

libc.headers-layouts
  + libc.pthread-tls

  + crt.static-pie

    -> owned static product

  + libc.c-abi-compat
  + crt.static-pie

## Required family transitions

The following sections define the remaining runtime transitions. The frozen
capability ledger supplies the exact selected surface within each named
capability; do not broaden it by assuming all of POSIX or all of musl.

### 1. `libc.headers-layouts`

This is the first required family transition.

Complete all installed-header obligations, not merely include success:

- public header pathname closure;
- strict, POSIX, X/Open, GNU, BSD, large-file, and other frozen feature
  profiles where selected;
- exact typedef, record, enum, constant, macro, data-object, and function
  declarations;
- C and required freestanding C++ linkage and name visibility;
- target-specific LP64/x87 layouts;
- transitive include behavior;
- materialized installed-tree isolation; and
- exact ownership routing for every selected public callable declaration.

Build a canonical callable-declaration inventory from the frozen headers and
ABI baseline. The existing `current-static-c-exports` ratchet is an input to
this audit. It must no longer stand in for it. Header closure requires exact
selected declarations, zero missing selected declaration names, and zero
undispositioned selected external callable names. A checked disposition is
either a current selected provider assignment or an exact named deferred
owner; it is not archive-extraction evidence.

A callable may be excluded only when the frozen profile excludes it. Record
that classification structurally. Do not hide unresolved declarations by
omitting a test profile, and do not let a deferred owner masquerade as an
implemented archive provider.

Promote `libc.headers-layouts` to `foundation-verified` only after one family
aggregate proves the complete installed surface, zero missing selected
declarations, and complete callable ownership routing. Do not continue an
open-ended sequence of independent header probes after that aggregate has
identified the finite missing rows.

### 2. `libc.posix-runtime`

This is the second required family transition. The private
`./scripts/dev-x86_64.sh libc-filesystem-directory` aggregate now selects the
frozen `filesystem.directory` roster through the opt-in `ftw`/`nftw` traversal
slice and the existing directory-stream and `scandir` artifacts. That
selection leaves the family planned and nonpublic; it is not a family
completion or promotion. Close the three remaining missing semantic
capabilities as subsystem batches:

- `process.control`;
- `process.signal`; and
- `system.kernel-admin`.

Integrate existing selected-private leaves into complete public C runtime
contracts with real errno/TLS, process startup, cancellation policy where
applicable, record ownership, aliases, and installed-header linkage. Do not
confuse the already complete Rust facade equivalents with C ABI completion.

Partition implementation into coherent filesystem, process/lifecycle,
environment, signal, and kernel-administration blocks. A block may contain
many musl source mappings and generated routine rows. It closes only when the
selected capability’s behavior, aliases, errors, concurrency/process-global
state, negative scope, and aggregate evidence are complete.

Then run the family’s differential, OS, signal-process, and libc-test-equivalent
native gates and promote the family.

### 3. `libc.pthread-tls`

Close:

- `thread.pthread-c11`;
- `time.posix-timer-thread-notify`; and
- the family-wide TLS/TCB/cancellation/fork interactions required by the
  frozen profile.

Unify the existing private static-thread artifacts into one owned runtime
model. Complete all selected pthread and C11 lifecycle, identity,
synchronization, attributes, thread-specific data, detach/join, cancellation,
cleanup, atfork/fork, signals, timer callback, errno, and exit interactions.

Static and dynamic processes must agree on TCB ownership. The loader,
`pthread_create`, main thread, runtime-loaded TLS modules, DTV growth,
`__tls_get_addr`, cancellation state, and fork child repair may not each own
incompatible private models.

`static-c-pthread-attributes` is bounded private evidence, not a family
transition: `./scripts/dev-x86_64.sh libc-pthread-attributes` compares one
project-header fixture with pinned musl 1.2.6 and a freestanding static
candidate. It selects only the 18 standard `pthread_attr_t` metadata entries:
initialization/destruction and set/get pairs for detach state, stack size,
stack, guard size, scope, inherit-scheduler state, scheduler policy, and
scheduler parameters. The private x86 record keeps musl's 56-byte align-eight
layout, 131072-byte stack and 8192-byte guard defaults, and its direct input
validation/status behavior; it does not make `pthread_create` consume an
attribute record. Custom-stack, detached-at-create, scheduler, and guard
runtime effects; GNU default attributes; `pthread_getattr_np` and live-thread
inspection; TLS/runtime integration; family promotion; and public x86 support
remain outside this leaf.

Do not promote the family from a collection of bounded worker fixtures. Its
aggregate must exercise realistic multi-threaded composition, stress the
selected synchronization and lifecycle paths, and prove static and dynamic
TLS behavior through owned artifacts.

### 4. `libc.text-math-locale-stdio`

Close the remaining frozen selected behavior for:

- `text.iconv`;
- `text.wide-multibyte`;
- `pattern.regex`;
- `pattern.wordexp`;
- `stdio.stream-io`;
- `stdio.path-stream`;
- `stdio.position-buffering`;
- `stdio.format-scan`; and
- `time.clock-calendar`.

Preserve the project’s restricted locale policy: `C`, `POSIX`, and `C.UTF-8`,
with UTF-8 Rust-facing text. Do not create a general locale or encoding
provider.

Treat stdio as one coherent stream engine with locking, buffering, byte/wide
orientation, permanent and created streams, descriptor adoption, positions,
errors, flushing, ordinary-exit interaction, formatted I/O, and the selected
memory/cookie/path stream behavior. Stop adding fixed observations of one
permanent stream when they do not advance that engine.

Treat math by coherent function families sharing algorithms, tables, fenv,
x87/MXCSR, long-double, errno, and exception behavior. Generate ordinary
signature and differential cases; retain bespoke tests for rounding,
exceptions, NaN payloads, long-double ABI, or compiler transformations.

Promote only after the family aggregate and installed consumers exercise the
composed runtime rather than isolated archive extractions.

### 5. `libc.resolver`

Complete the bounded resolver selected by the frozen profile:

- conventional `/etc/hosts`, `/etc/resolv.conf`, `/etc/services`, and

- A, AAAA, and CNAME processing;
- search behavior;
- UDP with TCP fallback;
- timeout, retry, server failover, response validation, and result lifetime;
- public netdb/resolver interfaces, state, errors, and thread interaction; and

Reuse the already completed Rust resolver transport and owned-record work where
its semantics and ownership fit, but implement the selected C state and ABI
rather than exporting a superficial wrapper. Do not add NSS, plugins, mDNS,
DoH, DoT, DNSSEC, or IDNA policy.

The existing numeric codecs and DNS-parser leaves are prerequisites, not
resolver completion. Promote the family only after end-to-end local-file and
controlled-network tests pass through the owned C runtime.

### 6. `libc.c-abi-compat`

Close:

- `crypto.crypt`;
- `crypto.crypt-helpers`;
- `memory.allocator-basic`;
- `legacy.misc`;
- `process.globals`; and
- final callable-provider/archive closure and binding compatibility for the

Do not hand-roll cryptography. Reuse the existing approved project primitive,

Close `memory.allocator-basic` through the accepted production allocator

Generate the complete public callable/data-object manifest from the frozen
headers and ABI input. Verify symbol names, aliases, bindings, visibility,
sizes, versions where selected, and static/shared ownership. Do not equate
matching symbol presence with semantic correctness; the corresponding owning
capability and family evidence must also be complete.

### 7. `ldso.dynamic-runtime`

Replace the current fixed and bounded graphs with the general selected loader

- `runtime.loader`;
- `runtime.private-facades`;
- `loader.dlfcn-basic`; and
- `loader.dlfcn-introspection`.

The finished loader must provide the frozen selected behavior for:

- interpreter self-relocation and process entry;
- main executable discovery;
- arbitrary admitted `DT_NEEDED` graph traversal rather than one fixed graph;
- selected search and RUNPATH/RPATH policy;
- file validation, mapping, load bias, protections, RELRO, and cleanup;
- all frozen x86-64 relocation kinds, symbol lookup, weak/global/protected

- supported RELA and RELR processing;
- loader-owned object graph state and RuntimeV1 publication;
- initial, initial-exec, and dynamic TLS, DTV growth, and thread integration;
- constructor and destructor ordering;
- `dlopen`, `dlsym`, `dlclose`, `dlerror`, `dladdr`, `dlinfo`, and
  `dl_iterate_phdr` selected behavior;
- valid/invalid close handles, retained mappings and reopen state, NODELETE
  behavior where selected, process-exit finalization, and failed-load rollback;
- locking, callback boundaries, concurrent operations, fork interaction, and
  admitted reentrancy; and
- fail-closed behavior without ambient loader fallback.

For musl 1.2.6 parity, successful `dlclose` validates the handle but does not
unmap the object or invoke its destructors. Reopening observes the retained
object; DSO destructors remain process-exit work. Physical last-close unloading
is not a completion requirement or a behavior to call musl parity. This does
not weaken cleanup of mappings owned by failed load transactions. The source
contract is musl's
[`src/ldso/dlclose.c`](https://git.musl-libc.org/cgit/musl/plain/src/ldso/dlclose.c?h=v1.2.6)
and [`ldso/dynlink.c`](https://git.musl-libc.org/cgit/musl/plain/ldso/dynlink.c?h=v1.2.6)
at release `9fa28ece75d8a2191de7c5bb53bed224c5947417`.

Use the existing fixed-graph, bounded runtime-mapping, TLS, dlfcn, diagnostic,
and owned-CRT artifacts as regression seeds. Do not extend them indefinitely
one condition at a time. Refactor their proved mechanisms into the general
loader and keep the fixed cases as focused regression fixtures.

Promote only when installed dynamic applications and DSOs exercise the general
runtime through the public shared-libc and CRT boundary.

### 8. `crt.dynamic-startup`, `sysroot.static-tls`, and `sysroot.owned-artifact`

Complete the CRT and installed-artifact chain as product integration, not as
more isolated link fixtures.

`crt.dynamic-startup` must own real dynamic `crt1`/`Scrt1` entry,
loader-to-libc handoff, main-image lifecycle arrays, process finalizer,
`__libc_start_main` interaction, ordinary exit, compiler-helper linkage, and
the supported PIE/non-PIE modes.

`sysroot.static-tls` must close through the independent owned-static product
gate described below.

`sysroot.owned-artifact` must install, manifest, reproduce, package, extract,
and smoke all selected static and dynamic modes using:

- the complete installed project header tree;
- owned CRT objects;
- owned `libc.a` and shared libc;
- owned interpreter and compatibility alias;
- owned compiler-builtins archive;
- the accepted allocator backend;
- deterministic static and dynamic link specifications; and
- no ambient target runtime input.

The compiler used to translate sources may come from the pinned development
environment. The target headers, startup objects, libraries, loader, helper
archives, and link decisions must come from the installed crabc artifact.

## Owned static product gate

Add a single campaign-level static integration suite. It may contain multiple
small fixtures, but it must be consumed as one product gate.

It must build from the materialized installed sysroot and cover both static
`ET_EXEC` and static PIE. The suite must jointly exercise:

- argument, environment, auxiliary-vector, and program-name publication;
- Initial TLS, errno, and high-alignment initialized and zero-filled TLS;
- allocator allocation, alignment, reallocation, failure, and remote-thread
  ownership;
- pthread/C11 creation, join/detach, synchronization, once, TSD, cancellation,
  atfork/fork, and exit behavior selected by the baseline;
- stdio creation, buffering, byte/block/formatted operations, positions,
  errors, and exit flushing;
- pathname, descriptor, directory, metadata, process, signal, and time paths;
- local socket transport and bounded resolver behavior;
- constructors, destructors, `atexit`-class behavior, and ordinary/immediate
  termination selected by the profile; and
- at least one owned compiler helper that fails to link when the crabc
  builtins archive is removed.

For every final executable, inspect the link trace, map, ELF headers, dynamic
section, relocations, symbol ownership, TLS segments, stack flags, and
interpreter absence. Reject undeclared target inputs before executing the
fixture.

The static gate is complete only when two clean installed builds and one
extracted install produce and run the same declared suite reproducibly.

## Owned dynamic product gate

Add one campaign-level dynamic integration suite using an installed main
program, an initially loaded dependency graph, and at least one runtime-loaded
plugin. It must cover both dynamic PIE and dynamic non-PIE where the frozen
profile selects both.

The suite must jointly prove:

- the installed interpreter path and compatibility alias;
- shared-libc loading and loader-to-libc RuntimeV1 handoff;
- dependency search, repeated dependencies, symbol scope, weak/global/
  protected behavior, and frozen supported relocations;
- main, dependency, and plugin constructors and destructors in correct order;
- process finalization, retained mappings across `dlclose`, reopen state, and
  destructor dispatch at process exit (not physical last-close unloading);
- `dlopen`, `dlsym`, `dlclose`, `dlerror`, `dladdr`, `dlinfo`, and
  `dl_iterate_phdr` behavior;
- initial-exec and general-dynamic TLS in initially loaded and runtime-loaded
  DSOs;
- DTV growth before and after worker creation;
- allocator, errno, stdio, pthread/TSD, signal, and exit interaction across
  DSO boundaries;
- concurrent open/lookup/close, callback execution, and admitted loader
  reentrancy;
- fork child repair where selected; and
- clean failure for malformed, unsupported, missing, stale, or cyclic inputs
  required by the selected profile.

Inspect every installed and fixture ELF. Reject ambient libc, loader, CRT,
libgcc, compiler-rt, target headers, or undeclared DSO search paths. The oracle
execution must remain a separate pinned-musl process, never a candidate
fallback.

The dynamic gate is complete only when two clean installed builds and one
extracted install pass the same suite reproducibly.

## Qualification families

After the runtime and product gates are complete, close the remaining required
families in their ledger dependency order.

### `compat.abi-differential`

Run the frozen ABI, header, static/shared symbol, alias/binding, record-layout,
relocation, and behavioral differentials against the pinned baseline and musl
oracle. Differences require an existing selected-profile justification or a
new explicit compatibility decision consistent with scope; they may not be
silently normalized away.

### `compat.posix-process`

Run the complete selected OS/libc/pthread/signal/process stress and regression
surface through owned x86 artifacts. Include process-global state, child
isolation, cancellation, fork, signal delivery/return, descriptor lifetime,
and concurrency interactions rather than only pure leaf functions.

### `compat.resolver-network`

Run deterministic local-file and controlled UDP/TCP resolver scenarios,
including timeout, retry, failover, truncation/TCP fallback, malformed replies,
search behavior, concurrency, and result lifetime.

### `compat.loader-corpus`

Run synthetic malformed/adversarial loader cases and the frozen selected real
software corpus through the owned interpreter and shared libc. Fixed private
loader graphs remain regression tests but cannot substitute for this family.

### `consumer.rust-std-lto`

Reproduce the frozen AArch64 Rust-standard-library and LTO consumer contracts
on x86 through the owned runtime and installed artifacts. Prove the selected
LTO modes do not reintroduce ambient runtime objects or unresolved compiler
helpers.

### `consumer.source-build`

Build and run the same frozen selected source projects used by the AArch64
contract, with equivalent configuration and no target-runtime fallback. Do not
replace a failing selected consumer with a smaller custom program.

### `capability.accounting`

Regenerate the final inventory from the immutable baseline. Require every
capability and family to be complete, every source digest to match its declared
input, every product and qualification gate to be current, and no unsupported
surface to have been counted as progress.

### `performance.release`

Run release-mode native x86 performance qualification after correctness is
closed. Investigate regressions at the architectural or algorithmic source;
do not weaken the contract merely to promote the platform. SIMD remains a
measured, separately proved optimization, not a shortcut around scalar
correctness.

## Evidence architecture

Every coherent implementation block needs three levels of evidence:

1. **Focused evidence** for its exact contract and failure modes.
2. **Family aggregate evidence** proving composition with the other members of
   the required family.
3. **Product or qualification evidence** proving that the installed runtime
   actually consumes the result.

A focused test may use direct archive extraction to isolate ownership. Family
and product tests must use the natural composed archive/shared-library and
installed-artifact boundary. Do not infer composition from a collection of
isolated extraction tests.

For each C/POSIX boundary:

- cite the exact pinned source or ABI owner;
- preserve source and license provenance;
- prove C and selected C++ declarations and linkage;
- prove errno, TLS, output-write, alias, binding, and lifetime behavior where
  observable;
- compare a separately launched pinned-musl oracle arm when behavior is not
  fully specified by an ABI;
- inspect the final candidate for unintended target inputs; and
- record intentional differences once, structurally, at the nearest semantic
  boundary.

Do not repeat a complete negative-scope essay in every generated leaf. Put
common exclusions at family level and record only the leaf-specific exception.

## Parallel implementation and worktree contract

Use one coordinator/integration owner and bounded, independently mergeable
work packages under the current user and agent-routing rules. Never use Terra
or Sol without explicit user authorization. Available concurrency is a ceiling,
not a target; do not invent leaf work to fill slots.

Parallelize dependency-ready implementation where interfaces and file ownership
are stable, using isolated worktrees and build outputs under checkout-local
`.work/`. Read-only scouting and review are useful independent assignments,
but their reports do not count as completed implementation. Coordinate runtime
and allocator work as described in `plan.md`.

### Coordinator ownership

The coordinator owns:

- the frozen baseline and campaign validator;
- the active machine-readable work plan;
- canonical `parity.toml` changes;
- generated inventory snapshots;
- the merged static-export ratchet;
- top-level dispatcher and generated command/module registries;
- dependency-order decisions;
- cherry-pick/rebase sequencing;
- aggregate family and product verification; and
- final promotion.

The coordinator retains cross-cutting design and final verification; delegate
bounded independent implementation when authorized workers are available.

### Worker ownership

Each worker receives a coherent package with:

- one subsystem ownership band;
- one target transition or named blocker;
- a defined base commit;
- source and test paths it owns;
- exact focused and aggregate evidence expectations; and
- explicit shared-spine changes to return as a fragment or integration note.

A worker implements, tests, and commits its package in its worktree. It does
not independently regenerate or settle the global ledger, counts, dispatcher,
or status prose after every leaf. It returns a clean commit plus a compact
machine-readable result containing the package ID, blocker removed, tests run,
known dependencies, and requested central integration changes.

### Suggested ownership bands

Use these as a starting partition and subdivide only around real ownership
boundaries:

1. header/profile/callable-inventory generation;
2. remaining header layout, data-object, and C++ linkage closure;
3. POSIX directories and filesystem extensions;
4. POSIX process control;
5. POSIX signals and kernel-administration surface;
6. pthread/C11 lifecycle and synchronization;
7. TLS/TCB/DTV, cancellation, fork, and timer-thread notification;
8. stdio stream/path/position engine;
9. formatted input, text, regex, and word expansion;
10. locale, iconv, wide/multibyte, math/fenv, and clock/calendar blocks as
    disjoint subpackages where file ownership permits;
11. bounded C resolver and netdb integration;
12. C ABI compatibility, allocator integration, crypt, and process globals as
    disjoint subpackages;
13. general loader mapping, graph, relocation, and scope;
14. loader TLS/dlfcn/lifecycle plus dynamic CRT handoff; and
15. static/dynamic sysroot, consumer, qualification, accounting, and
    performance preparation.

Do not assign two workers overlapping mutable runtime state without first
fixing the ownership boundary. Do not let every worker edit the central static
C registry, dispatcher, export file, parity ledger, and status documents.

### Merge protocol

For each wave:

1. Freeze the coordinator’s base commit and work-package manifest.
2. Start independent implementation worktrees from that base.
3. Require focused tests in each worker branch.
4. Review and merge in dependency order, not completion-arrival order.
5. Resolve central fragments once per coherent batch.
6. Run affected family aggregates after each merge group.
7. Regenerate the campaign status once per merge group.
8. Remove completed worktrees only after their commits and evidence are
   integrated.
9. Reassign freed slots immediately to the next dependency-ready blockers.

Do not use repeated global rebases or broad formatting as a merge strategy.
Preserve unrelated work. Never push a remote unless the user explicitly asks.

## Final promotion protocol

product, or qualification obligation:

1. Create a fresh detached native x86 worktree at the proposed final commit.
2. Verify the immutable baseline and exact 223-capability/26-family roster.
3. Build all owned artifacts from clean caches or isolated output directories.
4. Run `campaign-all`.
5. Build the installed sysroot twice and compare the declared artifact trees.
6. Extract the packaged sysroot into a fresh location and rerun the complete
   static and dynamic product suites against the extracted copy.

    unrelated changes.

## Prohibited failure modes

Never do any of the following during this campaign:

- schedule work from the next unlisted static export;
- claim progress from artifact or export count alone;
- add a bespoke C probe, C++ probe, assembly `_start`, shell runner,
  dispatcher case, ledger essay, and status paragraph for a routine leaf that
  the family matrix can express;
- mark a family complete because its easiest symbols or private fixtures pass;
- treat a Rust-facade capability as proof of its public C ABI counterpart;
- treat a fixed loader graph as the general loader;
- let a pinned-musl oracle object enter a candidate final link;
- use glibc or ambient host behavior to fill a missing contract;
- hide final C-ABI provider/archive failures through archive non-extraction;
- refresh the AArch64 baseline to eliminate x86 work;
- make static delivery wait on dynamic startup after the dependency correction;
- postpone all loader architecture until every unrelated C compatibility leaf
  is complete;
- broaden locale, resolver, crypto, platform, or dependency scope;
- resume AArch64 allocator work or substitute allocator tests for runtime gates;
- edit CI workflows;
- run broad formatters, linters, or pre-commit hooks without explicit user
  direction;
- stop at a settlement checkpoint and call it full completion; or
- append implementation history to this execution contract.

The only successful terminal state is the exact full-completion predicate
above.
