# Native Linux/x86-64 runtime parity goal

## Status and scope

This is the active plan for bringing `crabc`, `crabc-libc`, `crabc-ldso`, the
CRT/sysroot, and `crabc-rs` to the same selected capability boundary as the
current Linux/AArch64 runtime.

It authorizes native Linux/x86-64 little-endian work only, with Linux 5.10 as
the kernel baseline. It does not authorize AArch64 emulation, another
architecture, a portability framework, or public x86-64 support. Until every
promotion gate below passes, Linux/AArch64 little-endian remains the only
supported public platform.

This document is deliberately a forward-looking goal and handoff. The exact
completed evidence belongs in
[`compat/x86_64/parity.toml`](compat/x86_64/parity.toml) and
[`compat/x86_64/README.md`](compat/x86_64/README.md), not in a growing list of
historical one-command checkpoints.

## What parity means

Parity is semantic coverage of the selected AArch64 runtime profile, not a
symbol count or a mechanical C-wrapper count. Each selected capability needs
an x86-64-native implementation, any required target ABI/layout proof, and
repeatable native evidence.

The completed target includes all of the following:

- `crabc-core`: x86 syscall, ELF/vDSO, TLS/thread-pointer, atomics/futexes,
  signal-frame, floating-point, and typed kernel-record foundations.
- `crabc-rs`: the same useful native runtime capability accounting as AArch64,
  exposed as an idiomatic Rust layer rather than a C ABI mirror.
- `crabc-libc`: the selected C/POSIX runtime, headers/layouts, errno/TLS,
  pthread/TLS, filesystem/process/signal/time/socket/resolver behavior, and
  text/locale/math/stdio profile.
- `crabc-ldso`, CRT, builtins, and an owned sysroot: native static and dynamic
  startup, dynamic loading, TLS, linking, and source-build behavior.
- Native qualification: ABI and behavioral differentials, OS/libc/pthread/
  resolver/loader gates, Rust-std/LTO consumers, source builds, capability
  accounting, and required performance evidence.

The retained profile remains the one in [`SCOPE.md`](SCOPE.md) and
[`COMPATIBILITY-PROFILE.md`](COMPATIBILITY-PROFILE.md): musl 1.2.6 is the C
and POSIX oracle; Rustix is test-only; glibc is never an oracle or fallback;
the resolver is bounded to conventional system files and A/AAAA/CNAME over
UDP/TCP; and there is no NSS, DoH/DoT, mDNS, IDNA policy, general locale
database, or hand-written cryptography.

Fixed mimalloc port work and evidence expansion are paused. Its retained
native x86 evidence is private allocator provenance, not progress toward this
runtime target.

The active AArch64 libc allocator backend is a separate matter from that
paused port. One private x86 artifact now builds the exact shared
`allocator_mimalloc.rs` wrapper and `libmimalloc-sys` 0.1.49 backend behind an
opt-in feature, proves all nine `memory.allocator-basic` C entries (`malloc`,
`calloc`, `realloc`, `reallocarray`, `free`, `aligned_alloc`,
`posix_memalign`, `memalign`, and `valloc`) against pinned musl, and rejects
every musl allocator object from the candidate link. Pinned musl still
supplies that candidate's startup and process primitives, and the bundled
backend object retains private `mi_*` globals. This therefore advances the C
allocator wrapper boundary without selecting an owned x86 runtime, the fixed
mimalloc v3.5.0 Rust port, allocator-family closure, or public support.

One separate opt-in mixed-runtime C-string-duplication client now maps musl
`strdup` and `strndup` through that wrapper without widening its completed
nine-entry object. Its exact client object owns only those two strong C entries
plus a private witness; the call to the prior weak `malloc` ABI and its
initial-TLS overflow errno path remain explicit. The musl differential rejects
musl's two duplicate and all nine allocator objects, then covers high-byte
ownership, bounded and zero-limit results, stale errno across `free`, and
full/bounded protected-page edges. Pinned musl still supplies startup/process
primitives, so this is neither `memory.allocator-basic` nor
`text.byte-strings-stateful`, allocator lifecycle/interposition/failure
injection, full C text/runtime closure, fixed-mimalloc-port progress,
promotion, or public x86 support.

The exact AArch64 `memory.allocator-observability` surface is now separately
selected as one complete private capability: strong `malloc_usable_size`, with
null returning zero and live pointers delegated directly to the active
backend's `mi_usable_size`. Its native candidate replaces the earlier
mixed-runtime startup assumption with real crabc `crt1.o`/`crti.o`/`crtn.o`,
static startup, Initial TLS v1, errno, allocation, pthread create/join/TSD/
mutex, mapping, clock, and wait/exit owners. Its current static-startup
composition also publishes the already-selected bounded environment,
program-name, and auxiliary-vector leaves before the fixture's callbacks.
Pinned-musl x86 and active crabc
AArch64 executions cover null, zero-size, small/large, calloc, aligned,
reallocated, post-join remote-thread, and contained inherited-child pointers,
including repeatability and errno preservation. The contained raw x86 fork is
fixture plumbing rather than public fork/atfork ownership. The unchanged
bundled mimalloc backend still requires exactly fourteen pinned-musl support
archive members. The current crabc startup owns `__environ`/`getenv`; the
candidate-local clone of pinned `libc.lo` weakens only its duplicate
`__progname`/`__progname_full` data while retaining `__libc`/`__hwcap` support.
The link gate rejects every musl allocator, observer, startup/TLS, pthread,
mapping, clock, and wait owner. This selects neither
`memory.allocator-basic` nor full runtime/allocator-family closure, the paused
fixed mimalloc v3.5.0 Rust port, promotion, or public x86 support.

`./scripts/dev-x86_64.sh libc-alloca` is a separate allocation-adjacent
compiler-builtin/header artifact, not another allocator vertical. The project
`alloca.h` byte-matches pinned musl 1.2.6 and maps the public spelling to
`__builtin_alloca`; C/C++ probes reject a callable `alloca` reference. Its
positive-size nested-frame fixture runs through pinned musl and a true
archive-free `-nostdlib -static` candidate, which rejects allocator/runtime
symbols, TLS, dynamic linkage, and a PLT while proving compiler-emitted stack
storage. It selects neither `memory.allocator-basic` nor
`memory.allocator-observability`, or alloca zero-size, VLA/unwind,
stack-overflow/guard, heap/lifecycle/interposition, CRT/sysroot, promotion, or
public x86 support.

## Current starting point

The parity ledger records a verified native foundation: pinned-musl oracle
provenance, x86 architecture primitives, a broad but bounded direct
`crabc-rs` subset, selected source-only C runtime leaves plus private static C
archive boundaries, checked relative loader/image work, and a static-PIE CRT
foundation. The CRT-only test is deliberately no-TLS; its fixture supplies a
test-local successful bootstrap stub only to keep checked relocation and
lifecycle evidence independent of libc. The separately recorded
`libc-static-tls-v1` artifact owns a private final-static-executable template
for the bounded pthread artifacts. The composed
`libc-crt-static-tls` artifact links real Rust `rcrt1.o`/`crti.o`/`crtn.o`
objects with that hidden libc owner, proving the non-preemptible static-link
handoff through an `R_X86_64_RELATIVE` slot before archive-owned
preinit/init/main/ordinary-exit/fini for one initialized/TBSS/high-alignment
image. Its bounded no-allocation exit block is not general process lifecycle
support. The companion `libc-crt1-static-tls` artifact links real Rust
`crt1.o`/`crti.o`/`crtn.o` through an ordinary static `ET_EXEC` final link and
uses the same TLS-first shared startup handoff before that bounded lifecycle.
It does not claim rcrt1 self-relocation, dynamic entry, or a sysroot route.
Neither CRT composition artifact selects general pthread/TLS, dynamic or
loader TLS, general CRT/libc startup, an owned sysroot, or public support. The direct
facade also now exposes the pure,
allocation-free `pattern::{fnmatch, FnmatchFlags}` byte matcher and
alloc-gated explicit-root `pattern::{GlobPath, glob, glob_at}` traversal.
Their x86 no-std archive proofs reject public C pattern, directory-stream,
errno, and allocation boundaries; the glob probe intentionally supplies its
own fixed Rust allocator. These are Rust-only native slices, not C
`fnmatch`/`glob`/`globfree` ABI support or public x86 support. The direct
facade also includes a complete socket/address transport family: socket lifecycle,
IPv4/IPv6 UDP, IPv4 TCP, typed options, `SIOCATMARK`, and vectored/batched
messages. Its first record-owning network vertical slice also has native x86
evidence: explicit-socket interface index/name ioctls, allocation-free link
enumeration, and owned link/address snapshots from fixed rtnetlink records. A
second private core slice proves caller-owned DNS UDP/TCP exchange behavior.
A third private facade slice selects the alloc-backed resolver and owned hosts
snapshot. A fourth private facade slice selects the owned services and
protocols snapshots, completing the three conventional netdb files. A fifth
private facade slice completes the selected filesystem path-core boundary:
typed descriptor-relative metadata and pathname lifecycle operations, links
and rename, bounded timestamp mutation, and caller-buffered plus owned

selects the direct `filesystem.xattr` family: caller-buffered binary values and

A ninth private facade slice selects `filesystem.extended-metadata`: direct

`filesystem.cwd-mutation`: bounded byte-preserving physical pathname resolution

`process::chroot<P: PathArg>` byte paths use direct `chroot=161` and return

## Parallel work lanes

To keep throughput high without erasing dependency boundaries, work may fan
out along these lanes:

- **Facade lane:** `facade.record-owning` is foundation-verified by the closed
  aggregate of its private slices. Keep that surface closed while the C-runtime
  artifact chain advances; reopen it only for a deliberate profile change.
- **C-runtime lane:** header/layout closure and errno/TLS integration, then
  selected C/POSIX and pthread/TLS behavior. It may proceed alongside facade
  work but must converge before the ABI-compatibility gate.
- **Runtime-artifact lane:** loader image/relocation and static-PIE foundations
  are already available; dynamic loader/CRT/sysroot work begins once its C

For every block:

1. Read the governing scope/profile/status documents and the relevant AArch64
   implementation, tests, and ledger entries.
2. Specify the exact native contract and write focused observable regressions.
3. Implement the target-specific code without emulation or ambient fallback.
4. Add native raw-kernel and/or pinned-musl evidence for every ABI boundary,
   then run the focused native command and the relevant aggregate lane.
