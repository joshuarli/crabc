# Native Linux/x86-64 runtime parity goal

## Status and scope

This is the active plan for bringing `crabc`, `crabc-libc`, `crabc-ldso`, the
CRT/sysroot, and `crabc-rs` to the same selected capability boundary as the
current Linux/AArch64 runtime.

It authorizes native Linux/x86-64 little-endian work only, with Linux 5.10 as
the kernel baseline. It does not authorize AArch64 emulation, another
architecture, a portability framework, or public x86-64 support. Until every
promotion gate below passes, Linux/AArch64 little-endian remains the only
supported public platform.

This document is deliberately a forward-looking goal and handoff. The exact
completed evidence belongs in
[`compat/x86_64/parity.toml`](compat/x86_64/parity.toml) and
[`compat/x86_64/README.md`](compat/x86_64/README.md), not in a growing list of
historical one-command checkpoints.

## What parity means

Parity is semantic coverage of the selected AArch64 runtime profile, not a
symbol count or a mechanical C-wrapper count. Each selected capability needs
an x86-64-native implementation, any required target ABI/layout proof, and
repeatable native evidence.

The completed target includes all of the following:

- `crabc-core`: x86 syscall, ELF/vDSO, TLS/thread-pointer, atomics/futexes,
  signal-frame, floating-point, and typed kernel-record foundations.
- `crabc-rs`: the same useful native runtime capability accounting as AArch64,
  exposed as an idiomatic Rust layer rather than a C ABI mirror.
- `crabc-libc`: the selected C/POSIX runtime, headers/layouts, errno/TLS,
  pthread/TLS, filesystem/process/signal/time/socket/resolver behavior, and
  text/locale/math/stdio profile.
- `crabc-ldso`, CRT, builtins, and an owned sysroot: native static and dynamic
  startup, dynamic loading, TLS, linking, and source-build behavior.
- Native qualification: ABI and behavioral differentials, OS/libc/pthread/
  resolver/loader gates, Rust-std/LTO consumers, source builds, capability
  accounting, and required performance evidence.

The retained profile remains the one in [`SCOPE.md`](SCOPE.md) and
[`COMPATIBILITY-PROFILE.md`](COMPATIBILITY-PROFILE.md): musl 1.2.6 is the C
and POSIX oracle; Rustix is test-only; glibc is never an oracle or fallback;
the resolver is bounded to conventional system files and A/AAAA/CNAME over
UDP/TCP; and there is no NSS, DoH/DoT, mDNS, IDNA policy, general locale
database, or hand-written cryptography.

Fixed mimalloc port work and evidence expansion are paused. Its retained
native x86 evidence is private allocator provenance, not progress toward this
runtime target.

## Current starting point

The parity ledger records a verified native foundation: pinned-musl oracle
provenance, x86 architecture primitives, a broad but bounded direct
`crabc-rs` subset, selected source-only C runtime leaves plus private static C
archive boundaries, checked relative loader/image work, and a static-PIE CRT
foundation. The CRT-only test is deliberately no-TLS; its fixture supplies a
test-local successful bootstrap stub only to keep checked relocation and
lifecycle evidence independent of libc. The separately recorded
`libc-static-tls-v1` artifact owns a private final-static-executable template
for the bounded pthread artifacts. The composed
`libc-crt-static-tls` artifact links real Rust `rcrt1.o`/`crti.o`/`crtn.o`
objects with that hidden libc owner, proving the non-preemptible static-link
handoff through an `R_X86_64_RELATIVE` slot before archive-owned
preinit/init/main/ordinary-exit/fini for one initialized/TBSS/high-alignment
image. Its bounded no-allocation exit block is not general process lifecycle
support.
Neither static artifact selects general pthread/TLS, dynamic or loader TLS,
general CRT/libc startup, an owned sysroot, or public support. The direct
facade also now exposes the pure,
allocation-free `pattern::{fnmatch, FnmatchFlags}` byte matcher and
alloc-gated explicit-root `pattern::{GlobPath, glob, glob_at}` traversal.
Their x86 no-std archive proofs reject public C pattern, directory-stream,
errno, and allocation boundaries; the glob probe intentionally supplies its
own fixed Rust allocator. These are Rust-only native slices, not C
`fnmatch`/`glob`/`globfree` ABI support or public x86 support. The direct
facade also includes a complete socket/address transport family: socket lifecycle,
IPv4/IPv6 UDP, IPv4 TCP, typed options, `SIOCATMARK`, and vectored/batched
messages. Its first record-owning network vertical slice also has native x86
evidence: explicit-socket interface index/name ioctls, allocation-free link
enumeration, and owned link/address snapshots from fixed rtnetlink records. A
second private core slice proves caller-owned DNS UDP/TCP exchange behavior.
A third private facade slice selects the alloc-backed resolver and owned hosts

## Parallel work lanes

To keep throughput high without erasing dependency boundaries, work may fan
out along these lanes:

- **Facade lane:** `facade.record-owning` is foundation-verified by the closed
  aggregate of its private slices. Keep that surface closed while the C-runtime
  artifact chain advances; reopen it only for a deliberate profile change.
- **C-runtime lane:** header/layout closure and errno/TLS integration, then
  selected C/POSIX and pthread/TLS behavior. It may proceed alongside facade
  work but must converge before the ABI-compatibility gate.
- **Runtime-artifact lane:** loader image/relocation and static-PIE foundations
  are already available; dynamic loader/CRT/sysroot work begins once its C
  header, TLS, and ABI prerequisites are real artifacts rather than leaves.
- **Qualification lane:** extend deterministic x86 harnesses as each block
  lands. Full C/POSIX, corpus, Rust-std, source-build, accounting, and
  performance promotion waits for the artifact chain.

Do not turn a missing dependency into another tiny goal. When a subsystem has
several independent records or syscalls, plan and implement its full useful
contract together; split only where an actual safety, ABI, or artifact
dependency makes that necessary.
