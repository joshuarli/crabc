# Private Linux/x86-64 C `crypt(3)` evidence

`./scripts/dev-x86_64.sh libc-crypt` is a private static x86 compatibility artifact for the existing bounded C `crypt(3)` profile. It is neither C ABI family promotion, allocator integration, dynamic-runtime work, a sysroot claim, nor public x86 support.

The artifact selects only SHA-256-crypt (`$5$`) and SHA-512-crypt (`$6$`) with the canonical one-to-sixteen-character `Base64ShaCrypt` salt and bounded `sha_crypt::Params` rounds profile already established by `compat/crabc-rs/crypt-profile.md`. It accepts a key of at most 256 bytes before its NUL terminator and an accepted setting of at most 37 bytes before its NUL terminator; `libc/src/c_abi/x86_64/crypt.rs` scans at most 257 and 38 caller bytes respectively before returning the unsupported marker. Accepted key/setting bytes are copied into fixed local storage before output, so a previous `crypt` result or a `crypt_data.__buf` may safely supply either input to the same call. `crypt` owns one shared 260-byte `struct crypt_data` record: its four-byte `initialized` field precedes the 256-byte `__buf` result region. `crypt_r` receives the same full 260-byte caller record and writes only `__buf`, preserving `initialized`. A null key selects the empty key. A null setting produces `"*"` through public `crypt`, weak `crypt_r`, and private `__crypt_r`, while direct private SHA helpers leave a non-null output buffer unchanged. The fixture executes the actual public `crypt`/weak `crypt_r` exports plus every exported private `__crypt_*` entry, proves the caller-buffer address and trailing guard, and rejects all permanent test-only crypt exports. The process-shared `crypt` result has the historical non-reentrant ownership boundary: callers must serialize concurrent calls.

## Source and dependency provenance

`libc/src/c_abi/x86_64/crypt.rs` is a target-local C ABI adapter, not a translation of cryptographic source. It maps SHA-256-crypt and SHA-512-crypt digest/round/transposition/MCF work to the existing RustCrypto `sha-crypt` 0.6 `ShaCrypt` and `PasswordHasher` APIs; SHA-crypt base64 salt validation to the existing RustCrypto `base64ct` 1.8 `Base64ShaCrypt` API; and the public `crypt`, weak `crypt_r`, and private `__crypt_*` dispatch/output boundaries to the behavior of `libc/src/crypt_impl.rs`.

The exact selected AArch64 profile and dependency review remain authoritative in `compat/crabc-rs/crypt-profile.md`. For this x86-only artifact, `sha-crypt`'s alloc-enabled serializer temporarily reaches the final link's C `malloc`/`aligned_alloc`/`free` boundary through a local `GlobalAlloc` bridge. `x86-crypt` does not enable `x86-allocator-runtime` or `libmimalloc-sys`; the private mixed-runtime evidence deliberately resolves those three symbols from pinned musl and rejects ambient/mimalloc allocator providers. The feature combination with `x86-allocator-runtime` is a compile-time rejection until one provider owns all three allocation operations under a separately evidenced composition contract. No allocator API, backend, lifecycle, fallback, or integration is selected by this leaf.

Musl 1.2.6 remains the C ABI/differential oracle. Its `src/crypt/crypt.c` dispatch and `src/crypt/crypt_sha256.c`/`crypt_sha512.c` demonstrate the historical surface, while this project deliberately does not translate their cryptographic algorithms. The selected shared explicit-round SHA vectors run against pinned musl and the candidate. Candidate-only assertions establish the intentional profile differences: the dependency's canonical default-round MCF spelling and `*` for DES, BSDI, MD5-crypt, bcrypt, invalid/noncanonical settings, and other unsupported legacy formats.
